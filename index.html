NAT-Arten

Statisches NAT
1:1 – eine private fest auf eine öffentliche IP (z. B. Server).
Dynamisches NAT
n:m – private IPs bekommen eine freie IP aus einem öffentlichen Pool.
PAT / NAT-Overloading
n:1 – viele private Hosts teilen sich eine öffentliche IP. Unterscheidung über die Quell-Portnummer.

So läuft PAT ab

  1. PC1 und PC2 senden Anfragen ins Internet (Quelle: private IP + dynamischer Quellport).
  2. Router R2 ersetzt die Quell-IP durch die Inside-Global-Adresse und merkt sich die Ports (z. B. 1444, 1445) in der NAT-Tabelle.
  3. Pakete gehen zum Ziel; die Antwort kommt an IP+Port des Routers zurück.
  4. Router schaut in der NAT-Tabelle nach und übersetzt zurück auf die Inside-Local-Adresse.
  • Ports sind 16 Bit → theoretisch 65.536 Übersetzungen je öffentlicher IP, realistisch ca. 4.000.
  • PAT versucht den Originalport zu behalten. Ist er belegt, nimmt es den ersten freien Port aus derselben Portgruppe: 0–511, 512–1023, 1024–65535.

Erreichbarkeit von außen trotz PAT

Von außen gibt es keinen Tabelleneintrag → Paket wird verworfen. Lösung: Portweiterleitung (statischer Eintrag). Beispiel aus dem Unterricht: Minecraft-Server, UDP 19132 an der Fritzbox → 192.168.178.116.

IPv6 und Sicherheit

Mit IPv6 entfällt NAT: jedes Gerät hat eine global erreichbare Adresse. Der „Nebeneffekt-Schutz“ von NAT fehlt, also wichtiger: Firewall konsequent nutzen und ggf. Proxy (Standardport 8080) als Mittelelement: IP-Masquerading/Anonymisierung, Websites blockieren, Loadbalancing, Logging, Zugriffskontrolle, Caching.

Routingtabelle

Spalten: Netzwerk-ID · CIDR · Schnittstelle · Next-Hop. Direkt angeschlossene Netze haben keinen Next-Hop (---). Default-Route: 0.0.0.0/0 (IPv4) bzw. ::/0 (IPv6) → alles, was nicht spezifischer passt.

IPv6-Grundlagen · ICMP · NDP

Adressaufbau

  • 128 Bit, 8 Blöcke à 16 Bit in Hex: 2001:0db8:0000:0000:0000:ff00:0042:8329
  • Kürzen: führende Nullen pro Block weg, einmal eine Folge von Null-Blöcken durch :: ersetzen → 2001:db8::ff00:42:8329
  • Typisch: 64 Bit Präfix (Netz) + 64 Bit Interface-ID (Host).
  • Kein Broadcast mehr – stattdessen Multicast.

ARP (IPv4) → NDP (IPv6)

ARP: „Wer hat 192.168.1.1?“ als Broadcast (ff:ff:ff:ff:ff:ff), Antwort per Unicast mit MAC. In Wireshark Filter arp.

NDP (Neighbor Discovery Protocol) ersetzt ARP und läuft über ICMPv6 (Wireshark: icmpv6):

ICMPv6-TypNachrichtZweck
133Router Solicitation (RS)Client fragt an ff02::2: „Gibt es Router?“
134Router Advertisement (RA)Router liefert Präfix, Gateway (seine Link-Local) und M-/O-Flag
135Neighbor Solicitation (NS)MAC zu IPv6 suchen (= ARP-Request), DAD
136Neighbor Advertisement (NA)Antwort mit MAC (= ARP-Reply)
137Redirectbesserer Next-Hop

DAD (Duplicate Address Detection): Bevor ein Host eine Adresse nutzt, schickt er ein NS an die Solicited-Node-Adresse. Antwortet niemand, ist sie frei.

Merke: ICMP in der Firewall zu deaktivieren verschleiert Hosts und hilft gegen DoS. Bei IPv6 darf man ICMPv6 aber nicht komplett sperren, sonst funktioniert NDP nicht.

DHCPv4

DHCP verteilt automatisch IP-Konfiguration an Clients. Vorteile: weniger Fehler, zentrale Übersicht, einfache Administration, flexibel. Router und Server bekommen keine dynamische Adresse (statisch oder Reservierung). Kein DHCP-Server erreichbar → APIPA 169.254.0.0/16.

Subnetzmaskewie vereinbart
AusschlussbereichAdressen im Bereich, die nie vergeben werden (statische Server, Router)

Weitere mögliche Zuweisungen: NTP/Zeitserver, Proxy-Konfiguration. Optionen gibt es auf Ebene Server (gilt für alle Bereiche), Bereich und Reservierung – die speziellere gewinnt.

Reservierung: feste IP für eine bestimmte MAC (z. B. Drucker, Server). Dynamische Zuordnung: Adresse aus dem Pool für die Leasezeit; meldet sich der Client nicht, wird sie wieder frei. Ist der Pool voll, bekommt kein neuer Client eine Adresse.

DHCP-Request im Ethernet-Rahmen: ff ff ff ff ff ff 08 00 27 e2 ed 6e 08 00 45 00 …

  • Ziel-MAC (6 Byte): ff:ff:ff:ff:ff:ff → Broadcast
  • Quell-MAC (6 Byte): 08:00:27:e2:ed:6e → Client
  • Type (2 Byte): 08 00 → IPv4; danach beginnt der IP-Header (45 = Version 4, Headerlänge 20 Byte)

Weitere Aufgaben dort: DORA-Verlauf zeichnen, drei Inhalte des OFFER nennen (IP-Angebot, Maske, Leasedauer, Server-ID, MAC des Clients), begründen, warum REQUEST ein Broadcast ist.

Absicherung des DHCP-Servers

Rogue DHCP
Fremder DHCP-Server (z. B. WLAN-Router im Auslieferungszustand) antwortet schneller und verteilt falsche Gateways/DNS → Netz lahm oder Man-in-the-Middle. Clients akzeptieren jeden Server.
DHCP Starvation
Angreifer fordert mit gefälschten MAC-Adressen alle Adressen an. Der echte Server ist leer, danach spielt der Angreifer selbst DHCP-Server (DNS umleiten).
MaßnahmeWirkung
DHCP-Snooping am SwitchDHCP-Antworten nur von vertrauenswürdigen Ports → Rogue DHCP blockiert
Port Security (MAC-Limit)begrenzt MACs pro Port → Starvation erschwert
MAC-Filter (Zulassen-Liste) / Reservierungennur Clients der eigenen Gruppe bekommen eine Adresse
Autorisierung im Active DirectoryWindows-DHCP-Server vergibt erst nach Autorisierung in der Domäne
802.1X / NACnur authentifizierte Geräte ins Netz
DHCP-FailoverAusfallsicherheit: Lastenausgleich (beide aktiv) oder Hot Standby (einer in Bereitschaft); gemeinsamer geheimer Schlüssel

DHCP-Relay-Agent

Problem: Router trennen Broadcastdomänen, das DISCOVER erreicht einen Server in einem anderen Subnetz nicht.
Lösung: Relay-Agent auf dem Router nimmt den Broadcast an und schickt ihn als Unicast an die konfigurierte Server-IP (Cisco: ip helper-address). Er trägt seine Interface-IP im Feld giaddr ein, daran erkennt der Server, aus welchem Bereich er vergeben muss. Die Antwort geht per Unicast an den Relay, der sie ins Client-Netz weitergibt.

EUI-64 – Interface-ID aus der MAC

  1. MAC (48 Bit) in der Mitte teilen: FC99:47 | 75:CEE0
  2. FFFE einfügen: FC99:47FF:FE75:CEE0
  3. 7. Bit (U/L-Bit) des ersten Bytes umdrehen: FC = 1111 1100 → 1111 1110 = FE
  4. Ergebnis: FE99:47FF:FE75:CEE0 → Link-Local fe80::fe99:47ff:fe75:cee0

Kurzregel für das erste Byte: zweite Hex-Ziffer ±2 (0↔2, 4↔6, 8↔A, C↔E, 1↔3 …). Vorteil: eindeutig aus der MAC; Nachteil: das Gerät ist darüber verfolgbar (deshalb nutzt Windows standardmäßig zufällige IDs).

Abfragearten

Rekursiv
Client → seinem DNS-Server (Resolver): „Gib mir die fertige Antwort.“
Iterativ
Resolver fragt sich selbst durch: Root → „frag .de“ → .de → „frag bwi.de“ → bwi.de → IP.

Caching passiert am Rechner (ipconfig /displaydns, /flushdns), am Resolver, beim Provider, an der Fritzbox.

Reihenfolge der Namensauflösung (Client)

  1. Eigener DNS-Cache (ipconfig /displaydns). Jeder Eintrag hat eine TTL in Sekunden (3600 = 1 Stunde, 32 Bit).
  2. Lokale hosts-Datei. Heute z. B. zum Blockieren: 127.0.0.1 analytics.google.de, 127.0.0.1 lizenzserver.com
  3. DNS-Server (Resolver) fragen
  4. Klappt das nicht: NetBIOS-Namensauflösung

In ipconfig /displaydns steht der Eintragstyp als Zahl: 1 = A, 28 = AAAA, 2 = NS, 5 = CNAME, 6 = SOA, 12 = PTR, 15 = MX, 16 = TXT. Datenlänge bei IPv4 = 4 Byte. Cache leeren: ipconfig /flushdns.

SOA-Eintrag lesen

@  IN  SOA  localhost. root.localhost. (
        2024090101   ; Serial  (JJJJMMTTNN, bei jeder Änderung erhöhen)
        86400        ; Refresh (Sekundärer prüft alle 24 h auf Änderungen)
        7200         ; Retry   (nach Fehlschlag erneut nach 2 h)
        3600000      ; Expire  (so lange bleibt Sekundärer ohne Primären autoritativ)

Ausfallsicher: Zum primären einen sekundären DNS-Server für die Zone installieren. Damit die Zonenübertragung klappt, müssen beide auf der Registerkarte „Namenserver“ der Zone eingetragen sein.

DNSSEC · AD-Integration

DNSSEC (DNS Security Extensions) prüft DNS-Antworten mit digitalen Signaturen. Schutzziele: Authentizität (Antwort kommt vom echten Server) und Integrität (Daten unverändert). Keine Vertraulichkeit – dafür DNS over TLS (Port 853) / HTTPS. Schützt vor DNS-Spoofing (z. B. paypal.de wird auf Angreifer-IP aufgelöst).

Digitale Signatur

  1. Signieren: Hash des Datensatzes bilden und mit dem privaten Schlüssel verschlüsseln = Signatur.
  2. Prüfen: Signatur mit dem öffentlichen Schlüssel entschlüsseln → H1.
  3. Selbst den Hash über den empfangenen Datensatz bilden → H2.
  4. H1 = H2 → Signatur gültig. Hash ⇒ Integrität, privater Schlüssel ⇒ Authentizität.

X.509 / PKI: Eine CA (Certificate Authority) bestätigt per Zertifikat, dass ein öffentlicher Schlüssel zu jemandem gehört (Root-CAs, mmc-Zertifikatsverwaltung).

Neue Ressourceneinträge

EintragFunktion
RRSIGdie Signatur zu einem Datensatz; wird bei jeder Antwort mitgeliefert
DNSKEYöffentlicher Schlüssel zum Prüfen (ZSK und KSK)
NSEC / NSEC3beweist, dass ein Name nicht existiert (Verweis auf den nächsten Eintrag) → verhindert gefälschtes „gibt es nicht“
DSHash des KSK in der übergeordneten Zone → Vertrauenskette bis zur Root

ZSK (Zone Signing Key) signiert die Zoneneinträge. KSK (Key Signing Key) signiert nur den ZSK bzw. die DNSKEY-Einträge.

Prüfen beim Client: A-Record hashen → H1; RRSIG mit DNSKEY entschlüsseln → H2; vergleichen. nslookup kann kein DNSSEC, stattdessen PowerShell: Resolve-DnsName finance.secure.contoso.com -Type A -Server dns1.contoso.com -DnssecOk

Einer AD-Domäne beitreten

  1. Client bekommt IP im richtigen Netz; als DNS-Server die IP des DCs eintragen (nicht Router/Google!), denn der Client findet den DC über SRV-Einträge.
  2. Test: ping DC, nslookup gruppe4.si241.de
  3. sysdm.cpl → Computername → Ändern → Domäne gruppe4.si241.de (PowerShell: Add-Computer -DomainName gruppe4.si241.de -Restart)
  4. Mit Domänen-Konto anmelden, Neustart → Computerkonto liegt in AD unter „Computers“.

Typische Fehler: falscher DNS-Server am Client · DC nicht erreichbar (Firewall/Netz) · geklonte VMs mit gleicher SID → vorher sysprep /generalize · Uhrzeit weicht mehr als 5 Min ab (Kerberos) · Computername doppelt.

Troubleshooting-Strategien

Vorgehen aus dem Unterricht (Routing)

  1. Ping im eigenen Netz (vorher evtl. ping 127.0.0.1 für den eigenen Stack)
  2. Ping zum Standardgateway
  3. Ping zum Transfernetz (nächster Router)
  4. Ping ins Internet (prüft Default-Route 0.0.0.0/0 bzw. ::/0)
  5. Ping per Name: klappt die IP, aber nicht der Name → DNS-Problem

Reconnaissance & OSINT

Reconnaissance = Ausspähen eines Ziels, um später Zugriff zu erlangen (Phase 1 von Kill Chain und Pentest). Passiv: ohne Kontakt zum Ziel (OSINT). Aktiv: Ping Sweeps, Port-Scans, Fingerprinting.

OSINT (Open Source Intelligence, ursprünglich militärisch) = systematisches Sammeln und Auswerten von Infos aus frei zugänglichen Quellen: Social Media, Firmenwebsite, Stellenanzeigen, Handelsregister, DNS/Whois. Beispiel: Emil arbeitet bei der BWI und ist im Taubenzüchterverein → Name, E-Mail-Schema, Position, Hobby für gezieltes Phishing.

„Open“ heißt hier nicht Open-Source-Software, sondern: jeder darf es einsehen, ohne etwas zu hacken. Man setzt harmlose Puzzleteile zu einem Bild zusammen. Typische Quellen: Firmenwebsite mit Impressum, Stellenanzeigen (z. B. „Admin mit Erfahrung in Fortinet, VMware, Exchange 2016“ verrät Firewall, Virtualisierung und Mailsystem), LinkedIn/Xing (Name des IT-Leiters), Google, WHOIS, Zertifikatslisten, GitHub, Handelsregister, Metadaten von PDFs (Autor, Programmversion). Genutzt von Angreifern zur Vorbereitung, von Pentestern als erster Schritt, von Journalisten und von Firmen, die wissen wollen, was über sie bekannt ist.

Pentesting = beauftragter, simulierter Angriff (Red Team), z. B. als Nachweis für ISO-27001-Audits. Reconnaissance ist Phase 1, danach folgt die Enumeration.

OSINT begrenzen – persönlich: wenig Privates posten (Adresse, Geburtsdatum), unterschiedliche Passwörter. Unternehmen: wenige Infos nach außen, Awareness/Phishing-Kampagnen, BSI-Grundschutz, Patches, eigene Pentests. Recon abwehren: nur nötige Ports öffnen (443, 53, 25, 143, VPN), ICMP von außen sperren.

Red Team · Blue Team · SOC

Red Team
simulierte Angreifer: Schwachstellen finden, Erkennung umgehen, Ziele infiltrieren
Blue Team
Verteidiger: Angriffe rechtzeitig erkennen, abwehren, Schaden minimieren
Purple Team
beide arbeiten zusammen, Erkenntnisse fließen direkt in die Abwehr
SOC
Security Operations Center: zentrale Stelle, die rund um die Uhr Logs/Alarme überwacht (SIEM), Vorfälle bewertet und reagiert (Incident Response) – Blue-Team-Arbeit

Weitere Sicherheitsbereiche im Unternehmen: NetSec, AppSec, GRC (Governance, Risk, Compliance), CISO.

DDoS

Gezielte Überlastung eines Dienstes durch sehr viele Anfragen aus vielen Quellen, meist ein Botnetz (oft unsichere IoT-Geräte).

AngriffSchichtFunktionsweiseAbwehr
SYN-Flood4 (TCP)Ziel: Server auslasten. Viele SYN („Ich möchte eine Verbindung aufbauen“), Server antwortet SYN-ACK und hält den Port eine Zeit lang offen, das ACK („Bestätigung“) kommt nie → halboffene Verbindungen, bis keine Ports mehr frei sindSYN-Cookies, IPs begrenzen oder blockieren, halboffene Verbindungen früher schließen
UDP-Flood3/4Ziel: Netzwerk/Server. Sehr viele UDP-Pakete an zufällige Ports → hohe Paketlast; Bandbreite und Ressourcen von Netzgeräten/Servern voll. Ziel antwortet jeweils mit ICMP „Destination Unreachable“ICMP-Antworten begrenzen, Firewall, Rate Limiting
HTTP-Flood7Ziel: Webserver/Webanwendung. Sehr viele HTTP-Anfragen (GET/POST) → Webserver, Anwendung oder Datenbank überlastet, echte Nutzer kommen nicht mehr durchWAF, Rate Limiting, CAPTCHA, CDN
DNS-Floodmeist 7Ziel: DNS-Infrastruktur. Große Mengen DNS-Anfragen → DNS-Server überlastet, Namensauflösung gestörtRate Limiting, Anycast/mehrere DNS-Server

Merksatz aus dem Skript: HTTP belastet die Webanwendung, UDP vor allem Netzwerkressourcen und DNS den Namensauflösungsdienst.

Grundlage SYN-Flood: TCP-3-Way-Handshake SYN → SYN-ACK → ACK baut eine verbindungsorientierte Verbindung auf. Allgemeine DDoS-Abwehr: Rate Limiter, IDS/IPS, Scrubbing/CDN beim Provider.
